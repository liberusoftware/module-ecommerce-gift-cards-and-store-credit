# Adoption

What a host has to do, and what it has to decide first.

---

## 1. Your gift card codes are in plain text, and you cannot get them back

Start here. Everything else in this document is ordinary migration work; this is
the part with a decision in it that cannot be undone.

```php
// database/migrations/2024_10_10_000003_create_gift_cards_table.php
$table->string('code', 16)->unique();
```

Every code your merchants have ever issued is sitting in that column, readable by
anything that can read the table. A gift card code is a **bearer credential** —
whoever has it has the money — so that column is cash in:

- every database backup you hold, and every one you have ever taken;
- every read replica;
- every slow-query log that captured `select * from gift_cards where code = ?`;
- every `select *` a support tool has ever run;
- every staff member's reach who has table access.

None of that requires a breach.

**This module cannot hold those codes.** There is no column for them. So adopting
it means deciding what happens to the cards that are already out there, and there
are exactly three options.

### Option A — carry the balances over, retire the codes (recommended)

Import each card as a new account with its **current balance** as the issued
amount, mint a **new code**, and send it to the customer. The old code stops
working.

You are re-issuing credentials that have been sitting in plain text for however
long, which is the right thing to do about a credential you have to assume is
exposed. The cost is a customer email and some support load; the benefit is that
after the migration there is no recoverable code anywhere in your system.

```php
use Liberu\Ecommerce\GiftCardsAndStoreCredit\Actions\IssueAccount;
use Liberu\Ecommerce\GiftCardsAndStoreCredit\Data\{IssueInput, Money};
use Liberu\Ecommerce\GiftCardsAndStoreCredit\Enums\AccountKind;

foreach (DB::table('gift_cards')->whereNull('disabled_at')->orderBy('id')->cursor() as $old) {
    // Minor units by string arithmetic, never `(int) ($decimal * 100)`.
    // `(int) (19.99 * 100)` is 1998.
    [$units, $fraction] = array_pad(explode('.', (string) $old->balance), 2, '0');
    $minor = (int) ($units.str_pad($fraction, 2, '0'));

    if ($minor <= 0) {
        continue;   // Nothing to carry. Leave it behind.
    }

    $issued = (new IssueAccount())->handle(new IssueInput(
        kind: AccountKind::GiftCard,
        // Idempotent, so a migration that dies halfway can simply be re-run.
        issueKey: 'migrated:gift_card:'.$old->id,
        // The currency the card was actually sold in. If your data is all
        // `USD` because of the old column default, **stop and find out** —
        // see §1.1.
        amount: new Money($minor, strtoupper($old->currency)),
        customerId: $old->customer_id,
        teamId: $theTeamThatSoldIt,
        sourceReference: 'legacy:gift_card:'.$old->id,
        // Your call. See §1.2.
        expiresAt: $old->expires_at,
    ));

    // The one and only time this code exists. Hand it to whatever emails it,
    // in the same iteration, and do not write it anywhere.
    dispatch(new MailReplacementGiftCard($old->customer_id, $issued->code, $issued->account->reference));
}
```

Then, and this is the step nobody remembers:

```sql
-- Once you have verified the balances carried over.
DROP TABLE gift_card_transactions;
DROP TABLE gift_cards;
```

…and **rotate your backups**, or accept that historical backups still contain
live-looking codes that no longer open anything. The second is usually fine once
the old table is gone, and it is a decision worth making out loud rather than by
omission.

### Option B — keep the old cards working, on the old table, until they run out

Run both. New cards go through this module; old ones keep hitting the old
`GiftCard` model until their balances reach zero, and then the old table is
dropped.

Honest about what it costs: for as long as it lasts you have two gift card
systems, two balances to reconcile, and **the plaintext column is still there**.
Pick a date to stop, put it in a ticket, and treat the old table as an incident
that has been scheduled rather than a system.

### Option C — import the codes as hashes

Technically possible: for each old card, compute `Code::index()` and
`Code::hash()` from the existing 16-character code and write the row directly.
The old codes keep working and the plaintext column goes.

Do not do this unless you have to. The old codes were generated by
`strtoupper(Str::random(16))`, which collapses 52 letters onto 26 and leaves
**letters twice as likely as digits** — a distribution nobody chose. They have
also been in plain text for the life of your system. You would be carrying both
of those forward permanently in exchange for not sending an email.

If you do it anyway: `Code::normalise()` maps `I`, `L` and `O` onto `1`, `1` and
`0`, so two distinct legacy codes differing only in those characters collide on
the index. Check for that **before** you start, not after.

### 1.1 Your `currency` column probably lies

```php
$table->string('currency', 3)->default('USD');
```

Every row that was written without an explicit currency says `USD` whether or not
that is what the customer paid. This module has **no default currency** and will
not invent one, so a migration is where you find out.

If you sell in one currency, that is a five-minute check. If you sell in several,
do not trust the column: reconcile against whatever the card was sold on — the
order, the payment, the price list — and only then migrate. A card denominated in
the wrong currency is a balance that is wrong by an exchange rate, and this module
will refuse to redeem it against the right one rather than converting.

### 1.2 Decide what you are doing about expiry before you migrate

`expires_at` is nullable with no default here, and it is **written once and never
edited** — there is no path that changes it and `update` is false by name on the
policy.

So the value you migrate is the value forever. Two things worth knowing:

- Expiry in this module ends **redeemability, not the money**. An expired card
  keeps its balance, still shows it, and can still be credited. Nothing is
  zeroed.
- Many jurisdictions regulate or forbid gift card expiry. This module knows no
  law. If you are not certain your dates are lawful, **migrate them as null** —
  that is the safe direction, and adding an expiry later to a card that has none
  is not possible either, which is precisely the property that makes null safe.

## 2. The rest of the host code this replaces

| Host | Replacement |
| --- | --- |
| `App\Models\GiftCard` | `Liberu\…\Models\GiftCardAccount`, with no `balance`, no `code`, no `disabled_at` |
| `App\Models\GiftCardTransaction` | `Liberu\…\Models\GiftCardEntry`, append-only |
| `GiftCard::use(float, Order, ?string)` | `RedeemByCode` with a `RedemptionInput` |
| `GiftCard::refund(float, ?Order, ?string)` | `RecordCredit` with `CreditOrigin::Refund` or `::Reversal` |
| `GiftCard::disable(?string)` / `enable()` | `DisableAccount`. **There is no enable** — see `docs/domain.md` §4.6 |
| `GiftCard::canUse(float)` / `isActive()` | `$account->state()->isRedeemable()`, folded |
| `GiftCard::generateUniqueCode()` | `Code::mint()`, and you never see the result twice |
| `getMaskedCodeAttribute()` | `AccountData::maskedCode()` |
| `scopeActive()` / `scopeExpired()` | `GiftCardQuery`, and `AccountStatus` off the fold |
| `template_suffix` | Nothing. Presentation belongs to a presentation package |
| `note` | Nothing. `reason_code` on an adjustment, and it is a code |

Four host behaviours change in ways worth reading twice:

1. **`use()` returned `false` when it could not spend.** `RedeemByCode` throws
   `RedemptionRefused`. A boolean return is how a caller forgets to check.
2. **`use()` wrote the balance and then the transaction, unwrapped.**
   `RedeemByCode` writes one row, inside one transaction, under a row lock,
   against a balance folded from the database.
3. **`enable()` existed.** It does not here. Disabling is terminal and the
   recovery is a replacement card — `docs/runbook.md` §4.1 has the procedure.
4. **`code` was readable.** It is not. If anything in your application reads
   `$giftCard->code` for any reason, that reason has to be solved another way
   before you migrate, and the answer is almost always `reference` or
   `last_four`.

Delete the host's own migrations once you have migrated the data:

```
database/migrations/2024_10_10_000003_create_gift_cards_table.php
database/migrations/2024_10_10_000004_create_gift_card_transactions_table.php
```

This module claims **no bare table names** — a `SchemaTest` case asserts
`gift_cards` and `gift_card_transactions` do not exist in its own schema — so
there is no collision while both are present. That is what makes Option B
possible.

## 3. Installing

```bash
composer require liberusoftware/ecommerce-gift-cards-and-store-credit
```

Nothing boots. The package ships no `extra.laravel.providers`, so
`ModuleManagerServiceProvider` is the only registrar and only when named:

```dotenv
MODULES_ENABLED=…,ecommerce-gift-cards-and-store-credit
```

```bash
php artisan vendor:publish --tag=gift-cards-config
php artisan migrate
```

### The pepper, which is not optional

```bash
php -r 'echo base64_encode(random_bytes(32)), PHP_EOL;'
```

```dotenv
GIFT_CARDS_CODE_PEPPER="the output of that"
```

`Code::pepper()` **throws** if this is empty. It does not fall back to `''`,
because hashing under the empty string would work perfectly — cards would issue,
codes would redeem, nothing would fail — and the module's central guarantee would
be off with nobody aware of it.

Treat it like a signing key: in your secret manager, not in the repository, the
same value on every application server, and **backed up somewhere you can reach
in an incident**. Losing it makes every existing card unredeemable, because the
lookup index cannot be recomputed. Rotating it is a real operation with a real
cost — `docs/runbook.md` §5 has the procedure.

### The rest

```dotenv
GIFT_CARDS_CODE_HASH_COST=10      # measure your hardware; see the runbook
GIFT_CARDS_MAX_ATTEMPTS=5
GIFT_CARDS_ATTEMPT_DECAY=60
GIFT_CARDS_TEAM_MODEL="App\Models\Team"
GIFT_CARDS_TELEMETRY=false
```

## 4. The two tables

| Table | Holds |
| --- | --- |
| `ecommerce_gift_card_accounts` | The card or credit account: reference, kind, `code_index`, `code_hash`, `last_four`, currency, `expires_at`, tenancy |
| `ecommerce_gift_card_entries` | The ledger. Append-only. Every balance is a sum over this |

Both carry the `ecommerce_gift_card_` prefix. There is no separate store-credit
table: store credit is the same ledger with a different issue path, and two
tables would have meant two copies of the fold.

## 5. The listeners you write

This module subscribes to nothing it did not publish itself. Everything that
joins it to the rest of your commerce stack is yours, which is what keeps it
installable without any of them.

### Inbound: a refund whose destination is a gift card

**The wave 7 seam.** Refunds decides the amount and the destination; this records
it. Neither module knows the other exists.

```php
use Liberu\Ecommerce\GiftCardsAndStoreCredit\Actions\RecordCredit;
use Liberu\Ecommerce\GiftCardsAndStoreCredit\Data\{CreditInput, Money};
use Liberu\Ecommerce\GiftCardsAndStoreCredit\Enums\CreditOrigin;
use Liberu\Ecommerce\GiftCardsAndStoreCredit\Exceptions\AccountNotCreditable;

Event::listen(RefundApproved::class, function (RefundApproved $event): void {
    if ($event->refund->destinationKind !== 'gift_card') {
        return;
    }

    try {
        (new RecordCredit())->handle(new CreditInput(
            accountReference: $event->refund->destinationReference,
            // The refund's own key, reused. A fresh one per attempt guarantees
            // nothing at all.
            entryKey: 'refund:'.$event->refund->reference,
            amount: new Money($event->refund->amountMinor, $event->refund->currency),
            origin: CreditOrigin::Refund,
            sourceReference: $event->refund->reference,
        ));
    } catch (AccountNotCreditable) {
        // The card was stopped. The refund is still owed — send it somewhere a
        // customer can spend it, and do not swallow this.
        report(new RefundDestinationUnusable($event->refund));
    }
});
```

Note what is **not** caught: `CurrencyMismatch`. A refund in a currency the card
is not denominated in has no answer this module is entitled to give, and
swallowing it would silently drop somebody's money.

### Inbound: a checkout paying with a gift card

Checkout already models a gift card as a tender — an amount, a kind and a
reference — and deliberately does not maintain a balance. So the order is:
**redeem first, record the tender second**, because the reference Checkout stores
should name a movement that happened.

```php
use Liberu\Ecommerce\GiftCardsAndStoreCredit\Actions\RedeemByCode;
use Liberu\Ecommerce\GiftCardsAndStoreCredit\Data\{Money, RedemptionInput};
use Liberu\Ecommerce\GiftCardsAndStoreCredit\Exceptions\RedemptionRefused;

try {
    $redeemed = (new RedeemByCode())->handle(new RedemptionInput(
        code: $request->string('code')->toString(),
        // Minted when the step was entered and held for its life — not at click
        // time, which defeats the mechanism entirely.
        entryKey: $this->idempotencyKey,
        amount: new Money($amountMinor, $checkout->currency),
        // Required. Whatever identifies the presenter.
        throttleKey: $request->ip(),
        sourceReference: $checkout->reference,
    ));
} catch (RedemptionRefused $refusal) {
    // **Show the message. Never the reason.** `$refusal->reason` is for your log.
    // The only reason you may treat differently is `Throttled`, which a guesser
    // has already worked out from being throttled.
    return back()->withErrors(['code' => $refusal->getMessage()]);
}

(new RecordTender())->handle(
    $checkout,
    amountMinor: $redeemed->entry->amount->minor,
    kind: TenderKind::GiftCard,
    status: TenderStatus::Captured,
    reference: $redeemed->entry->id,   // or the account reference
);
```

**If the order then fails**, put it back with a reversal — a new entry carrying
the redemption's `source_reference`, never a deletion:

```php
(new RecordCredit())->handle(new CreditInput(
    accountReference: $redeemed->account->reference,
    entryKey: 'reversal:'.$checkout->reference,
    amount: new Money($redeemed->entry->amount->minor, $redeemed->entry->amount->currency),
    origin: CreditOrigin::Reversal,
    sourceReference: $checkout->reference,
));
```

### Outbound: a card was issued, so email the code

**The one thing a listener cannot do.** `GiftCardIssued` does not carry the code
and never will — a listener is not the caller, and an event goes to everybody. Do
it on the call that issued:

```php
$issued = (new IssueAccount())->handle($input);

Mail::to($customer)->send(new YourGiftCardMail($issued->code, $issued->account->reference));
```

And do not log it, queue it as a job payload, or put it in a notification body
that a database channel would persist. `$issued->code` should reach exactly one
place and then go out of scope.

### Outbound: alerting on somebody working through the code space

`RedemptionFailed` carries the reason the bearer was not told. A burst of
`RefusalReason::Unknown` against one `throttleKey` is what an enumeration attempt
looks like, and it is the single most valuable thing here to alert on.

```php
Event::listen(RedemptionFailed::class, function (RedemptionFailed $event): void {
    if ($event->reason === RefusalReason::Unknown) {
        YourAlerting::increment('gift-card.guess', ['presenter' => $event->throttleKey]);
    }
});
```

## 6. Surfaces

There is no `-filament`, `-api` or `-livewire` package for this module yet. When
you build one, four rules are not negotiable:

1. **Nothing about a code is searchable or filterable.** A search term and a
   filter both persist into the query string, into browser history, into your
   access logs and into anything that mirrors them. `GiftCardQuery` deliberately
   has no `byCode()` for the same reason.
2. **Never render `RedemptionRefused::$reason` to a bearer.** It is the whole
   anti-enumeration control. Show `getMessage()`.
3. **No money value is a client input.** Hold a reference and price it server-side
   on the request that acts.
4. **Mint an idempotency key when a step is entered**, hold it for that step's
   life, and send the same one on every retry. A key minted at click time defeats
   the mechanism entirely.

A conflict here means the key already recorded a **different** movement, so
minting a fresh one would debit the card a second time. Refuse and mint nothing —
the Payment Operations shape, not the Checkout one.

## 7. What you still have to build

- The panel or API that issues cards, and the thing that delivers the code.
- The refund and checkout listeners above.
- A reminder job over `GiftCardQuery::expiringBefore()`, if your jurisdiction
  allows expiry at all.
- A reconciliation queue over `GiftCardQuery::needingReconciliation()`, and
  somebody who reads it.
- Whatever your accountants need about breakage and unclaimed property. This
  module records balances and movements; it has no opinion about revenue
  recognition and no idea what escheatment is.
